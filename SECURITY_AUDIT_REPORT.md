# Outfit League security audit

**Review date:** 27 October 2026  
**Scope:** Local application source, Supabase Edge Functions and migrations, storage rules, Cloudflare Pages battle preview handlers, repository hygiene, and available local verification. Security hardening code is now deployed to the relevant production services. No production database data, Supabase project settings, or credentials were changed.

## Summary

Completed local hardening for authentication callbacks, battle share-image privacy, and guest-vote rate limiting. Fixed the existing TypeScript error in notification scheduling. Existing SSRF hardening for lookalike image fetching remains in place. The application UI and unfinished features were not redesigned or completed.

## Changes

### Authentication callback — fragment sessions removed

The Supabase client is configured with `flowType: "pkce"` and `detectSessionInUrl: false`. The app's email confirmation, password recovery, and OAuth entry points all use that client and redirect to the auth callback; recovery is carried as a query marker. The callback now exchanges only a PKCE `code`. A fragment containing `access_token` and `refresh_token` is ignored and can no longer install a session. Recovery markers in query/fragment remain readable, but fragment tokens are never used for authentication.

Regression tests cover PKCE parsing, recovery routing, router parameters, and rejection of a token-only fragment. This is safe for links generated by the current app flow. The hosted Supabase email templates and links already issued by production were not inspected; confirm a real sign-up, recovery, and OAuth round trip on web and iOS before publishing this local change.

### Battle image privacy — publication-checked image proxy

The `share-preview` action no longer creates 30-day signed Storage URLs. It returns only available image sides. Social metadata now points to stable `chutni.store/battle/{id}/image/{side}` URLs. The Pages image route calls the battles function, which checks that the battle is still published, reads the private image, validates the JPEG and its size, and returns it with a five-minute cache lifetime. Unpublished battles therefore stop serving new image responses; cached copies can remain available for up to five minutes at our endpoint.

WhatsApp and other supported crawlers retain stable, public preview URLs while the battle is published. Social platforms may keep their own cached or copied previews beyond our cache window, which the app cannot revoke. Previously issued 30-day Storage URLs also remain valid until they expire; the new code stops issuing them but does not change existing production URLs. The Pages site and compiled Functions worker are deployed to Cloudflare Pages. The homepage and battle app route load. The image proxy returned `Not found` for the previously shared sample battle ID, so a live published battle image and social-crawler metadata were not verified end to end.

### Anonymous battle voting — proportionate network throttles

Guests still vote without creating an account. The existing per-guest-token database rate limit remains in place. Server network limits now use only a validated `CF-Connecting-IP` value; caller-supplied `X-Forwarded-For` and `X-Real-IP` values are ignored. A valid edge IP receives an additional per-network hourly cap and a per-battle vote cap. IP addresses are hashed before they are used as rate-limit keys and are not returned to callers. If the trusted header is absent or invalid, network throttling is skipped and the per-guest-token database limit still applies.

The Supabase gateway's deployed header behavior has not been verified. Confirm that it overwrites or safely supplies `CF-Connecting-IP` before relying on the network limit. Guest identity can still be reset by clearing browser data or switching devices; a determined attacker can therefore evade per-token limits. No CAPTCHA or paid anti-abuse service was added.

The shopping outbound endpoint also stopped treating the first `X-Forwarded-For` value as trustworthy. Its network limit applies only when a valid edge client IP is present.

### Other fixes

- `src/lib/notifications.ts` now asserts the two fixed comeback-copy entries as present. This preserves behavior and resolves the existing TypeScript error.
- Lookalike image fetching continues to use the guarded public-asset fetch path: HTTPS only, DNS/private-address validation on redirects, timeout, streamed byte cap, and image MIME restrictions. DNS rebinding remains possible between validation and connection.

## Dashboard item: leaked-password protection

The Supabase dashboard was checked on 27 October 2026. Leaked-password protection is off. The dashboard indicates this feature requires the Pro plan. It was not enabled and no plan was changed.

To check it: open the Supabase project, go to **Authentication → Sign In / Providers → Email**, and inspect **Prevent use of leaked passwords**. If available, enable it and save; Supabase documents that leaked-password protection requires Pro or above. Then check **Authentication → Attack Protection** or rerun the Security Advisor to confirm the status. Do this in the dashboard only after reviewing the plan impact. See [Supabase password security](https://supabase.com/docs/guides/auth/password-security).

## Controls reviewed

- Private tables use RLS and owner scoping; service-only records/functions deny client access.
- Private image buckets are not public. Server paths validate owner, size, MIME, and dimensions.
- Try-on requires account authentication, explicit consent, owned assets, credit reservation, and idempotency; provider credentials remain server-side.
- RevenueCat webhook checks a server-only authorization secret and delegates idempotent grants to database functions.
- Account deletion blocks access, unpublishes battles, and queues durable storage cleanup.
- Public battles intentionally disclose published battle images and content by link. Private try-on inputs are not returned by battle views.
- Tracked-file inspection previously found only `.env.example` and `supabase/.env.server.example`; the web-release audit below found no private server secrets or environment files in the built web package. Publishable client keys are public by design and must remain protected by server authorization and RLS.
